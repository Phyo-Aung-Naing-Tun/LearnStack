# Chapter 2: Functions

Functions are the first line of organization in any program. Let's talk about how to write them well.

## Small!

The first rule of functions is that they should be small. The second rule of functions is that they should be smaller than that.

Functions should hardly ever be 20 lines long. Every function should be transparently obvious. Each should tell a story. And each should lead you to the next in a compelling order.

```java
// Bad — does too much, hard to understand
public static String renderPageWithSetupsAndTeardowns(
  PageData pageData, boolean isSuite) throws Exception {
  boolean isTestPage = pageData.hasAttribute("Test");
  if (isTestPage) {
    WikiPage testPage = pageData.getWikiPage();
    StringBuffer newPageContent = new StringBuffer();
    includeSetupPages(testPage, newPageContent, isSuite);
    newPageContent.append(pageData.getContent());
    includeTeardownPages(testPage, newPageContent, isSuite);
    pageData.setContent(newPageContent.toString());
  }
  return pageData.getHtml();
}

// Good — small and readable
public static String renderPageWithSetupsAndTeardowns(
  PageData pageData, boolean isSuite) throws Exception {
  if (isTestPage(pageData))
    includeSetupAndTeardownPages(pageData, isSuite);
  return pageData.getHtml();
}
```

## Do One Thing

**Functions should do one thing. They should do it well. They should do it only.**

The problem with this statement is that it is hard to know what "one thing" is. If a function does only those steps that are one level below the stated name of the function, then the function is doing one thing.

```java
// Bad — does THREE things
public void saveUserAndSendEmail(User user) {
  // 1. validate
  if (user.getName() == null) throw new Exception("Name required");
  // 2. save
  database.save(user);
  // 3. send email
  emailService.sendWelcome(user.getEmail());
}

// Good — each does ONE thing
public void registerUser(User user) {
  validateUser(user);
  saveUser(user);
  sendWelcomeEmail(user);
}

private void validateUser(User user) { ... }
private void saveUser(User user) { ... }
private void sendWelcomeEmail(User user) { ... }
```

## One Level of Abstraction per Function

In order to make sure our functions are doing "one thing," we need to make sure that the statements within our function are all at the same level of abstraction.

```java
// Bad — mixes high and low level abstraction
public String getPage(String url) {
  // High level
  String rawPage = download(url);
  // Low level (mixed in!)
  String[] lines = rawPage.split("\n");
  StringBuilder result = new StringBuilder();
  for (String line : lines) {
    if (!line.startsWith("//")) {
      result.append(line).append("\n");
    }
  }
  return result.toString();
}

// Good — consistent level of abstraction
public String getPage(String url) {
  String rawPage = download(url);
  return removeComments(rawPage);
}

private String removeComments(String page) {
  return Arrays.stream(page.split("\n"))
    .filter(line -> !line.startsWith("//"))
    .collect(Collectors.joining("\n"));
}
```

## Use Descriptive Names

Don't be afraid to make a name long. A long descriptive name is better than a short enigmatic name. A long descriptive name is better than a long descriptive comment.

```java
// Bad
private void wtf(int x, int y) { ... }

// Good
private void includeSetupPageInto(WikiPage page) { ... }
private void renderPageWithSetupAndTeardown(PageData data) { ... }
```

## Function Arguments

The ideal number of arguments for a function is zero (niladic). Next comes one (monadic), followed closely by two (dyadic). Three arguments (triadic) should be avoided where possible. More than three (polyadic) requires very special justification — and then shouldn't be used anyway.

```java
// Bad — too many arguments
Circle makeCircle(double x, double y, double radius);

// Good — use a Point object
Circle makeCircle(Point center, double radius);

// Even better with 0 args using builder pattern
Circle circle = Circle.builder()
  .center(new Point(x, y))
  .radius(radius)
  .build();
```

### Flag Arguments

Flag arguments are ugly. Passing a boolean into a function is a truly terrible practice. It immediately complicates the signature of the method, loudly proclaiming that this function does more than one thing.

```java
// Bad
render(true);  // what does true mean???

// Good — split into two functions
renderForSuite();
renderForSingleTest();
```

## Have No Side Effects

Side effects are lies. Your function promises to do one thing, but it also does other hidden things.

```java
// Bad — side effect: modifies session unexpectedly
public boolean checkPassword(String userName, String password) {
  User user = UserGateway.findByName(userName);
  if (user != null) {
    String codedPhrase = user.getPhraseEncodedByPassword();
    String phrase = cryptographer.decrypt(codedPhrase, password);
    if ("Valid Password".equals(phrase)) {
      Session.initialize(); // ← SIDE EFFECT!
      return true;
    }
  }
  return false;
}

// Good — make the side effect explicit in the name
public boolean checkPasswordAndInitializeSession(String userName, String password)
```

## Key Takeaways

- **Small** — functions should be 5–15 lines ideally
- **Do one thing** — if you can extract a function from it, it's doing more than one thing
- **One level of abstraction** — don't mix high-level logic with low-level detail
- **Descriptive names** — `includeSetupPageInto()` beats `isp()`
- **Minimal arguments** — 0 is ideal, 3+ is a smell
- **No side effects** — what you see should be what you get
