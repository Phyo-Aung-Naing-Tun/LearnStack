# Chapter 3: Comments

> "Don't comment bad code — rewrite it."
> — Brian W. Kernighan and P.J. Plaugher

Nothing can be quite so helpful as a well-placed comment. Nothing can clutter up a module more than frivolous dogmatic comments. Nothing can be quite so damaging as an old crufty comment that propagates lies and misinformation.

## Comments Do Not Make Up for Bad Code

One of the more common motivations for writing comments is bad code. We write a module and we know it is confusing and disorganized. We know it's a mess. So we say to ourselves, "Ooh, I'd better comment that!" No! You'd better clean it!

```java
// Bad — comment compensates for poor naming
// Check to see if the employee is eligible for full benefits
if ((employee.flags & HOURLY_FLAG) && (employee.age > 65))

// Good — self-documenting code, no comment needed
if (employee.isEligibleForFullBenefits())
```

## Good Comments

Some comments are necessary or beneficial. The only truly good comment is the one you found a way not to write. But some serve real purpose:

### Legal Comments

```java
// Copyright (C) 2026 by Object Mentor, Inc. All rights reserved.
// Released under the terms of the GNU General Public License v2.
```

### Explanation of Intent

```java
// We use a negative to distinguish the 'not found' case from
// an empty sequence. Without this, a count of 0 would be ambiguous.
return -1;
```

### Warning of Consequences

```java
// Don't run unless you have some time to kill.
public void _testWithReallyBigFile() { ... }
```

### TODO Comments

```java
// TODO: This is a workaround. Remove when the auth library is updated.
public String hackAuthToken() { ... }
```

### Amplification

```java
// The trim is real important. It removes the leading spaces that
// could cause the item to be recognized as another list item.
String listItemContent = match.group(3).trim();
```

## Bad Comments

Most comments fall into this category. Usually they are crutches or excuses for poor code or justifications for insufficient decisions.

### Mumbling

```java
// Bad — what does this mean?
try {
  // ...
} catch (Exception e) {
  // Couldn't load defaults
}
```

### Redundant Comments

```java
// Bad — the comment says exactly what the code says
// Utility method that returns when this.closed is true.
// Throws an exception if the timeout is reached.
public synchronized void waitForClose(final long timeoutMillis) throws Exception {
  if (!closed) {
    wait(timeoutMillis);
    if (!closed)
      throw new Exception("MockResponseSender could not be closed");
  }
}
```

### Misleading Comments

```java
// Bad — says "when" but actually means "if"
// This method returns when this.closed is true.
// It throws if timeout.
public synchronized void waitForClose(final long timeoutMillis) {
  // ...only if it times out, not just when closed!
}
```

### Mandated Comments

```java
// Bad — forced javadoc adds noise, not value
/**
 * @param title The title of the CD
 * @param author The author of the CD
 * @param tracks The number of tracks on the CD
 */
public void addCD(String title, String author, int tracks) { ... }
```

### Journal Comments

```java
// Bad — use version control instead!
// Changes (from 11-Oct-2026)
// --------------------------
// 11-Oct-2026 : Implemented equals() method
// 12-Oct-2026 : Fixed bug with null checks
```

### Noise Comments

```java
// Bad — states the obvious
/** The day of the month. */
private int dayOfMonth;

/** Default constructor. */
protected AnnualDateRule() {}
```

### Commented-Out Code

```java
// Bad — DELETE IT. That's what git is for.
// InputStream resultsStream = formatter.getResultStream();
// StreamReader resultsReader = new StreamReader(resultsStream);
// Response response = new Response();
String results = formatter.getResults();
```

### HTML in Comments

```java
// Bad — unreadable in the source file
/**
 * Task to run fit tests.
 * This task runs <b>fitnesse</b> fitness tests and publishes the results.
 * <p/>
 * @param targetDir The {@link File} indicating the directory to use.
 */
```

## Key Takeaways

- **Self-documenting code beats comments** — rename the variable/method instead
- **Good comments**: legal, intent explanation, warnings, TODOs, amplification
- **Bad comments**: redundant, misleading, mandated, journal, noise, commented-out code
- **Commented-out code = DELETE IT** — version control remembers it
- **If you feel the urge to write a comment** — first try to refactor the code so it doesn't need one
