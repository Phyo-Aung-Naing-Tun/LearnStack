# Chapter 1: Meaningful Names

Names are everywhere in software. We name our variables, our functions, our arguments, our classes, and our packages. We name our source files and the directories that contain them. We name and name and name. Because we do so much of it, we'd better do it well.

## Use Intention-Revealing Names

The name of a variable, function, or class should answer all the big questions. It should tell you why it exists, what it does, and how it is used. If a name requires a comment, then the name does not reveal its intent.

```java
// Bad
int d; // elapsed time in days

// Good
int elapsedTimeInDays;
int daysSinceModification;
int daysSinceCreation;
int fileAgeInDays;
```

The name `d` reveals nothing. It does not evoke a sense of elapsed time, nor of days. We should choose a name that specifies what is being measured and the unit of that measurement.

## Avoid Disinformation

Programmers must avoid leaving false clues that obscure the meaning of code. We should avoid words whose entrenched meanings vary from our intended meaning.

```java
// Bad — "List" implies a specific data structure
int[] accountList = new int[100];

// Good
int[] accounts = new int[100];
int[] accountGroup = new int[100];
```

Do not refer to a grouping of accounts as an `accountList` unless it's actually a `List`. The word "list" means something specific to programmers. If the container holding the accounts is not actually a List, it may lead to false conclusions.

## Make Meaningful Distinctions

Programmers create problems for themselves when they write code solely to satisfy a compiler or interpreter. If names must be different, then they should also mean something different.

```java
// Bad — what is the difference?
getActiveAccount();
getActiveAccounts();
getActiveAccountInfo();

// Good — clear intent
getActiveAccount();        // returns one account
getAllActiveAccounts();     // returns a collection
getActiveAccountDetails(); // returns full detail object
```

Number-series naming (`a1`, `a2`, `aN`) is the opposite of intentional naming. Such names are not disinformative — they are noninformative; they provide no clue to the author's intention.

## Use Pronounceable Names

If you can't pronounce it, you can't discuss it without sounding like an idiot. This matters because programming is a social activity.

```java
// Bad — hard to discuss out loud
class DtaRcrd102 {
  private Date genymdhms;
  private Date modymdhms;
  private final String pszqint = "102";
}

// Good
class Customer {
  private Date generationTimestamp;
  private Date modificationTimestamp;
  private final String recordId = "102";
}
```

## Use Searchable Names

Single-letter names and numeric constants have a particular problem: they are not easy to locate across a body of text.

```java
// Bad — how do you search for "5" or "e"?
for (int j = 0; j < 34; j++) {
  s += (t[j] * 4) / 5;
}

// Good — all terms are searchable
int realDaysPerIdealDay = 4;
const int WORK_DAYS_PER_WEEK = 5;
int sum = 0;
```

## Avoid Encodings

We have enough encodings to deal with without adding more to our burden. Encoding type or scope information into names simply adds an extra burden of deciphering. Encoded names are seldom pronounceable and are easy to mis-type.

```java
// Bad — Hungarian notation (obsolete)
PhoneNumber phoneString;
String strName;
int iCount;

// Good
PhoneNumber phone;
String name;
int count;
```

## Class Names

Classes and objects should have noun or noun phrase names like `Customer`, `WikiPage`, `Account`, and `AddressParser`. Avoid words like `Manager`, `Processor`, `Data`, or `Info` in the name of a class. A class name should not be a verb.

```java
// Bad
class DataManager {}
class InfoProcessor {}
class UserData {}

// Good
class Customer {}
class WikiPage {}
class AccountParser {}
```

## Method Names

Methods should have verb or verb phrase names like `postPayment`, `deletePage`, or `save`. Accessors, mutators, and predicates should be named for their value and prefixed with `get`, `set`, and `is`.

```java
// Bad
void process() {}
boolean check() {}

// Good
void postPayment() {}
void deletePage() {}
boolean isPosted() {}
String getName() {}
void setName(String name) {}
```

## Key Takeaways

- **Names should reveal intent** — if it needs a comment, rename it
- **Avoid disinformation** — don't use misleading names like `accountList` for an array
- **Make distinctions meaningful** — `getAccount()` vs `getAccountInfo()` should mean different things
- **Use pronounceable names** — you'll discuss code with colleagues
- **Use searchable names** — avoid single letters and magic numbers
- **Classes = nouns, Methods = verbs** — follow this pattern consistently
